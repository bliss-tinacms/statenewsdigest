Its stable archive-membership regression ID is `CATEGORY-ARCHIVE-MEMBERSHIP-ORDER-001`: every applicable destination must execute `load all posts → normalize complete assignments → filter by active category → paginate the filtered collection → render`, compute totals from the filtered collection, include multi-category posts in every assigned archive, remove unused template cards/pagers, and render exactly one explicit empty state with zero cards rather than falling back to all posts. `TINA-FULLCHECK` must enumerate actual category records, build a backend assignment oracle from every post's complete category array, and compare exact expected/rendered first-page slugs with zero unrelated slugs for every archive. `AUTHOR-ISLAND-EDITABILITY-001` applies whenever the site has an author/user/profile/contributor collection or public identity route. If that feature does not exist, record `NOT_APPLICABLE` with schema and route-inventory evidence; never silently omit the gate.

`ISLAND-RENDER-COMPLETENESS-001` applies to every configured collection and visible island region. It distinguishes the route's initial child render from the registry component used during visual-editor refresh. ## `SEO-REFLECTION-CHAIN-001` — permanent release-blocking control

This control activates automatically for every Astro/Tina migration, rebuild, repair, or deployment with any SEO-capable collection. It is not satisfied by fields appearing in Tina Admin, a successful Save, a correct card/list, an HTTP `200`, or visual similarity. `ASTRO-DEMO-LOCK` controls presentation only and can never authorize static, stale, or hard-coded Tina-managed SEO.

For every configured SEO-bearing collection and every canonical/alias public route, retain an executable mapping across the complete chain:

```text
Tina schema/content
→ generated type and query selection
→ authenticated backend response
→ application loader/data authority
→ shared SEO resolver
→ exact Astro route/layout props
→ decoded public DOM metadata and relevant JSON-LD
```

The destination must satisfy all of these invariants:

1. **Complete query authority:** every render-authoritative detail query selects every supported SEO field. A lightweight connection/list result may identify a document but may not become the rendering authority unless its completeness is machine-proven.
2. **One shared resolver:** title, description, canonical, robots, Open Graph, Twitter, images, and relevant structured-data precedence must be implemented once and imported by every applicable route. Required precedence is explicit Tina document SEO → document fields → Global Config defaults → deterministic site fallback. Route-local fallback forks are release failures.
3. **Freshness consistency:** when singleton/detail and connection/list payloads can diverge after a save, the route must select one complete, demonstrably fresh authority or compare freshness deterministically. A stale payload may never overwrite a fresher complete payload. The homepage/list and detail/archive surface for one record must converge on the same saved value.
4. **Positive contract tests:** repository-owned tests must prove schema coverage, generated/hand-written query coverage, resolver precedence, route-to-resolver wiring, metadata output completeness, canonical route mapping, and the intended data authority for Page, Blog/Post, Category, User/Author, Navigation, and Global Config where applicable.
5. **Controlled-negative canary:** a separate test must deliberately remove or corrupt, in temporary copies, at least: one full-document fetch, one SEO query field, one route-to-shared-resolver import, one freshness-precedence rule, and one rendered metadata output. Every controlled defect must be rejected for its intended invariant. A positive-only suite cannot unlock a release.
6. **Build wiring:** both positive and controlled-negative tests must run in the destination's normal validation/build path before an immutable artifact can be produced. A manually invoked optional script is insufficient.
7. **Authenticated public transaction:** `TINA-FULLCHECK` and `PUBLISHER-ADMIN-GATE` must mutate a uniquely observable SEO value through the live admin, prove the exact authenticated backend value, prove it on the correct cache-busted public route, restore it through the live admin, and prove backend/public exact restoration plus marker absence. The chosen field must actually control that public DOM location; mutating an ordinary description while an explicit SEO description controls `<meta name="description">` is an invalid test.
8. **Decoded DOM comparison:** compare browser-decoded title, description, canonical, robots, Open Graph, Twitter, image URLs, and relevant JSON-LD values. Raw source substring matching cannot certify values containing HTML entities or URL normalization.
9. **All-route audit:** enumerate every configured SEO-bearing document from the backend, derive its canonical route, and compare expected resolved SEO with the decoded live DOM. Configured counts must equal tested counts; sampling is forbidden.
10. **Restoration-first finalization:** isolate collection transactions so one failure cannot suppress later coverage, restore in `finally`, fetch all Tina mutation/restoration commits, prove zero marker residue, rebuild, and deploy only the exact restoration-tip SHA. Run the final all-route audit read-only after deployment.

The retained manifest must contain `seoReflectionChain` rows for every applicable collection/route and evidence for the positive suite, every controlled negative, full live transaction, all-route audit, exact restoration, zero residue, and final SHA equality. Any missing chain link, route, collection, negative, restoration proof, build wiring, or final deployed-SHA proof is `FAIL` or `BLOCKED`; it can never be waived as an indexing delay or visual-only issue.

## Completion rule

The umbrella result is computed by the global state machine and reusable completion validator; it is never asserted manually. `PASS`/`COMPLETE` is allowed only when the non-overridable evidence preflight passes, all component rules pass (or an explicitly permitted `NOT_APPLICABLE` row has rationale and evidence), the configured collection set exactly equals the collection evidence set, every editable route/island and required system class has retained proof, exact restoration/cleanup is empty, all final lineage SHAs are equal, and read-only verification of that final deployed SHA passes.

Run both:

```bash
node scripts/validate-migration-completion.mjs <retained-manifest.json>
node scripts/test-migration-completion-negative.mjs
```

The positive validator must exit `0` with `state=COMPLETE` and `completionEligible=true`; the negative suite must pass. Any missing, stale, representative, contradictory, failed, unavailable or unrun evidence locks completion language and makes the umbrella result `BLOCKED` or `FAIL`. Build success, HTTP `200`, a Git commit, push, deployment, endpoint availability, script name/exit code/success string, or verbal assurance can never unlock completion.
